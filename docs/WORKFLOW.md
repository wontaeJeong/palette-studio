# 에이전트를 더 잘 활용하는 방식

팔레트를 많이 미리 만드는 것은 탐색을 빠르게 합니다. 최종 UI 품질은 실제 컴포넌트·데이터·상태를 같은 조건으로 비교할 때 더 정확히 판단할 수 있습니다. 이 키트는 후보 카탈로그와 구현 계약 사이를 연결합니다.

## 작업별로 주는 자유도를 바꾸기

| 단계 | 에이전트에게 맡길 판단 | 고정할 기준 | 남길 결과 |
|---|---|---|---|
| 탐색 | 앱에 어울리는 2~3개 후보와 이유 | 같은 대표 화면·데이터·스타일 | 비교 화면과 구체적 차이 |
| 선택 | 선택 후보의 실제 제약·보완점 | 브랜드·기존 UX·변경 모드 | design-profile.json |
| 적용 | 기존 컴포넌트와 토큰의 매핑 | 선택 팔레트·스타일·상태 의미 | canonical CSS와 필요한 컴포넌트 수정 |
| 검토 | 실제 사용에서 드러나는 문제와 해결 | 대표 화면·작업 시나리오 | 확인 근거·예외·남은 문제 |
| 확장 | 새 화면에 맞는 구조 | 같은 디자인 계약 | 일관된 추가 화면 |

탐색 때부터 모든 세부 위치를 지정하면 앱 맥락에 맞는 판단 여지가 사라집니다. 반대로 적용 이후에도 색상·라운드를 매번 자유롭게 정하게 하면 화면마다 스타일이 흔들립니다. 후보 탐색에는 선택지를 주고, 채택 후에는 기준을 고정합니다.

## 실제 앱에서의 비교

색상 선택 때는 기존 sidebar·tabs·표·상태 배지·JSON 컴포넌트를 그대로 재사용합니다. 같은 긴 항목 이름과 한국어 설명, 같은 실패 메시지와 상태·심각도를 표시합니다. 새로운 예쁜 카드 레이아웃을 만드는 일과 색상 검증을 섞지 않습니다. 색상을 고른 다음 밀도·여백·형태를 별도로 조정하면 판단이 쉬워집니다.

이전 브랜드 유지가 우선이면 Graphite / Plum에서 출발하고, 다른 분위기를 탐색할 때 Slate / Indigo·Slate / Blue·Slate / Teal·Warm Stone / Sage 등 2~3개로 좁힙니다. 이는 후보 탐색의 출발점이며 객관적 우열 순위는 아닙니다.

## 요청을 구체화할 때 유용한 재료

- 대표 화면 2~3개와 사용자가 끝내야 할 실제 작업.
- 바꾸고 싶은 문제: 현재 메뉴가 안 보임 / 판정과 상태·심각도 혼동 / JSON과 배경 경계 불명확 등.
- 유지할 요소: 라이트 컬러, 로고, 기존 컴포넌트, 폰트 로더 등.
- 선택 프로필과 작은 결정 기록. 매번 전체 대화 이력을 읽히는 대신 짧고 안정적인 기준을 둡니다.

일반적인 코드 분석·빌드 절차를 장문으로 반복할 필요는 없습니다. Superpowers가 기존 워크플로를 수행하게 하고 화면의 실제 요구와 채택한 디자인 기준에 집중해 지시하세요. `agents/SCREEN-BRIEF.md`, `COMPARE-CANDIDATES.md`, `APPLY-PROFILE.md`가 이 흐름의 템플릿입니다.

## Studio에서 디자인 선택하기

한 화면에서 시작 세트 → 세부 조정 → 확인·내보내기로 진행합니다. 왼쪽에서 색상·형태·본문/코드 글꼴을 고르고, 필요한 경우 배치·움직임·컴포넌트·아이콘을 펼쳐 조정합니다. 기능별 탭이나 다른 편집 페이지로 이동하지 않습니다.

오른쪽에는 같은 프로젝트 UI가 계속 표시됩니다. Light/Dark를 함께 보거나 두 팔레트를 비교할 수 있습니다. 모바일에서는 축소 미리보기를 확인하고 필요할 때 확대합니다. 입력에 포커스하면 확대 미리보기는 접혀 편집을 가리지 않습니다.

상단 **확인 · 내보내기**에서 프로젝트와 색상 적용 범위·프레임워크·폰트 공급 방식을 확인합니다. 모든 CSS·프로필·작업지시·설정 JSON은 같은 선택값에서 생성됩니다. 본문과 코드 글꼴은 독립적으로 선택하며 도구의 다크 UI와 프로젝트의 적용 범위도 구분합니다.
