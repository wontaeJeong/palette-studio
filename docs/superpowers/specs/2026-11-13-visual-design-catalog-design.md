작성일: 2026-11-13 (Asia/Seoul)

기준: `main`의 `d07f65205b9b3262a7ad29081f7523c16a715d71`

## 1. 목적과 사용자 결정

웹 디자인 요소의 이름을 잘 모르는 바이브코더가 완성된 화면을 보고 출발점을 고르고, 세부 요소를 눈으로 비교해 다듬은 뒤, 코딩 에이전트에게 재현 가능한 구현 지시를 전달한다.

사용자가 확정한 방향:

- 기본 사용 흐름은 **완성된 화면 프리셋 선택 → 세부 요소 조정 → 작업 프롬프트 생성**이다.
- **컴포넌트 도감은 독립적인 핵심 기능**이다. 프리셋의 부속 도움말이나 후속 단계로 축소하지 않는다.
- 이름을 몰라도 찾기, 충분한 디자인 후보의 미리보기, 색상·디자인 선택, 에이전트 전달까지 연결해야 한다.

이하 프리셋 수, 컴포넌트 수, 화면 구성과 파일 구조는 위 방향을 구현하기 위한 제안이다. 승인된 사용자 지시와 구현자의 제안을 혼동하지 않는다.

## 2. 현재 상태와 제약

- `index.html` / `app.js`: 색상 → 스타일 → 폰트 → 내보내기, 고정된 프로젝트 대시보드, 기본 상태 견본. 컴포넌트별 레시피 선택·보관 기능은 없다.
- 32개 팔레트, 6개 형태·밀도 스타일, 역할별 OFL 폰트 24종, Lucide 아이콘 95개를 재사용한다.
- `handoff.html`, `data/handoff-core.js`, `scripts/create-design-handoff.cjs`가 설정·프로필·CSS·문서·작업지시를 생성한다. 현재 프로필 2.0.0에는 개별 컴포넌트 결정이 없다.
- 브라우저 UI와 Node CLI가 공통 생성 규칙을 사용해야 한다. `app.js`의 기존 간단 프롬프트와 확장 핸드오프의 선택 정보가 갈라지는 문제도 함께 정리한다.
- 서버 없이 실행되는 HTML/JS, 로컬 저장, URL fragment, 오프라인 배포를 유지한다. 기존 React 아이콘 패키지는 유지한다.
- 팔레트 원본 생성, 직접 HEX 의미 토큰, 폰트·아이콘 라이선스, 단일 테마 체계와 변경 scope 규칙은 기존 `AGENTS.md`를 따른다.

## 3. 접근법과 선택 근거

| 접근 | 장점 | 비용과 제약 | 결정 |
|---|---|---|---|
| 요소를 처음부터 하나씩 조합 | 개별 디자인 탐색의 자유 | 시작할 때 결정이 많고 전체 조화를 직접 판단해야 함 | 도감의 독립 진입 경로로 지원 |
| 완성 화면 프리셋에서 출발하고 필요한 요소만 교체 | 즉시 비교 가능하며 전체 일관성을 확보 | 완성 프리셋과 레시피 매핑의 품질이 중요 | 사용자가 선택한 기본 흐름 |

구현은 현재 Vanilla HTML/CSS/JS 구조를 확장하는 안을 제안한다. 이번 목적에 필수적이지 않은 React/Vite 전면 전환이나 백엔드 도입은 포함하지 않는다. 프레임워크 전환보다 카탈로그·선택·재현 계약을 먼저 완성한다.

## 4. 성공 기준, 범위와 피할 결과

성공은 사용자가 이름을 몰랐던 요소를 찾아, 후보의 외형과 동작을 비교하고, 실제 화면에서 조합을 판단한 뒤, 그 선택이 빠짐없이 기록된 작업지시를 얻는 것이다.

첫 구현 범위는 화면 프리셋 6세트, 화면 유형 4종, 컴포넌트 36종, 각 컴포넌트의 시각적으로 구별되는 레시피 최소 3개다. **도감과 프리셋·핸드오프 연결까지 하나의 첫 구현 범위**로 취급한다. 도감을 미완성 목록으로 남겨 두고 프리셋 화면만 완성했다고 하지 않는다.

범위 밖: 임의 좌표 드래그 편집기, 페이지 빌더, 실제 백엔드 업무 처리, 계정·협업 서비스, 자동 웹사이트 생성·배포, 외부 LLM 호출. 실제 서비스의 업무 로직은 데모에서 실행하지 않는다.

피할 결과:

- 동일한 요소에 색만 바꾼 것을 서로 다른 레시피로 집계하기.
- 영문 컴포넌트 이름을 알아야만 이용 가능한 검색과 메뉴.
- 모든 조합을 동일한 SaaS 대시보드에만 보여 주기.
- 도감에는 있지만 선택하거나 프롬프트로 전달할 수 없는 장식용 견본.
- 선택한 프리셋이 사용자의 세부 수정을 조용히 지우는 동작.
- 특정 색상, 폰트, UI 라이브러리 또는 장식 양식을 모든 프리셋에 강제하기.

## 5. 탐색 구조와 두 가지 사용자 여정

상위 영역은 `화면 프리셋`, `컴포넌트 도감`, `내 디자인`, `확인·내보내기`로 제안한다. 색상·스타일·폰트·아이콘은 내 디자인을 다듬는 도구로 계속 접근할 수 있다. 다운로드는 마지막 확인 단계에 둔다.

### A. 기본 여정: 완성 화면에서 시작

1. 같은 화면 유형·문구·데이터를 사용하는 프리셋 썸네일을 비교한다.
2. 프리셋을 적용하면 팔레트·폰트·형태·밀도·컴포넌트 레시피가 한 세트로 선택된다.
3. 큰 화면 미리보기에서 라이트/다크, 화면 유형과 모바일 폭을 전환한다.
4. `요소 선택` 모드를 켜고 토스트·버튼·표 등을 선택하면 해당 요소의 현재 선택과 다른 레시피가 열린다.
5. 도감에서 후보를 비교하거나 실행한 뒤 `내 디자인에 적용`한다.
6. 변경한 화면을 확인하고 작업지시와 프로필을 내보낸다.

요소 선택 모드는 일반 데모 조작 모드와 구분하며, 선택 중이라는 표시와 키보드로 접근 가능한 요소 목록을 제공한다. 모드를 끄면 실제 데모의 클릭·입력 동작으로 돌아온다.

### B. 독립 여정: 도감에서 먼저 찾기

1. 프리셋 선택 없이도 도감을 열어 생김새·용도·검색어로 요소를 찾는다.
2. 쉬운 설명, 정식 이름, 비슷한 요소와의 차이, 레시피를 확인한다.
3. 현재 팔레트로 후보들을 나란히 비교하고 실제 동작을 실행한다.
4. 현재 디자인에 적용하고 화면 미리보기로 이동하거나 도감 탐색을 계속한다.

두 여정은 같은 선택 상태를 공유한다. 도감 진입 때문에 별도 프로젝트나 두 번째 테마 상태가 만들어지지 않는다. 프리셋을 명시적으로 고르지 않았을 때에는 현재 또는 기본 선택을 사용하고, 기본값임을 표시한다.

## 6. 완성 화면 프리셋

다음 6세트를 제안한다. 기존 스타일 ID를 재사용하며, 표의 팔레트는 초기 추천값이다. 모든 세트는 이후 다른 팔레트로 변경할 수 있다.

| 프리셋 | 스타일 | 초기 팔레트 | 시각적 기준 |
|---|---|---|---|
| 차분한 업무형 | operational | slate-blue | 작은 라운드, 명확한 계층, 중립 면과 제한된 포인트 |
| 부드러운 제품형 | soft | pearl-lavender | 넉넉한 간격, 부드러운 모서리, 은은한 면 |
| 선명한 테두리형 | outline | neutral-monochrome | 작은 모서리, 선 중심 구획, 단정한 컨트롤 |
| 타이포 중심형 | editorial | paper-ink | 제목·본문 위계, 읽기 폭, 글 중심 정보 표현 |
| 조밀한 운영형 | compact | slate-steel | 조밀한 표·도구 모음, 짧은 동선, 데스크톱 정보 밀도 |
| 명확한 경계형 | contrast | navy-cyan | 또렷한 경계와 포커스, 명확한 선택 상태 |

각 프리셋은 단순한 색상·스타일 별칭에 그치지 않는다. 본문/코드 폰트 추천, 아이콘 표현, 요소별 기본 레시피와 밀도 값을 포함한다. 폰트는 기존 카탈로그 안에서 선택하며 한글 본문을 읽을 수 있어야 한다. 인증되지 않은 접근성 등급을 프리셋 이름이나 설명으로 주장하지 않는다.

화면 유형은 `대시보드·목록`, `설정·입력 폼`, `문서·위키`, `랜딩·소개` 네 가지다. 6세트를 네 화면에서 모두 확인할 수 있게 하되, 24개 독립 페이지를 복제하지 않고 공통 화면 템플릿에 선택값을 적용한다. 기존 `layout`과 매핑은 각각 dashboard, workflow, content, marketing이다. 기존 앱의 `layout=existing`은 그대로 유지할 수 있으며 미리보기 화면을 바꿨다는 이유로 변경하지 않는다.

화면 데이터는 동일한 한국어·영어 샘플을 사용하며 샘플임을 표시한다. 프리셋을 바꿔도 유리한 문구·차트·데이터로 바꾸지 않는다. 기존 샘플 차트는 재사용하되, 이번 36종에 전문 차트 편집기를 포함하는 것은 아니다.

## 7. 컴포넌트 도감의 필수 범위

| 분류 | 컴포넌트 | 수 |
|---|---|---:|
| 동작·입력 | Button, Input, Textarea, Select, Combobox, Checkbox, Radio Group, Switch, Segmented Control, Slider, File Upload | 11 |
| 이동·탐색 | Tabs, Sidebar, Breadcrumb, Pagination, Dropdown Menu, Command Palette | 6 |
| 겹쳐 여는 화면 | Dialog, Alert Dialog, Drawer/Sheet, Popover | 4 |
| 안내·피드백 | Toast/Snackbar, Tooltip, Alert/Callout, Banner, Progress, Skeleton | 6 |
| 내용·데이터 | Card, Badge, Avatar, Accordion, Table, List, Timeline, Empty State, Error State | 9 |
| 합계 | | 36 |

### 7.1 찾기

- 한국어 이름, 영문 이름, 일상 설명, 별명과 사용 상황을 검색한다. 별도 AI 검색 없이 카탈로그의 검증 가능한 검색 메타데이터로 구현한다.
- 필수 예: `잠깐 뜨는 알림`, `저장 완료` → Toast; `가운데 확인창` → Dialog/Alert Dialog; `옆에서 나오는 창` → Drawer; `마우스 올리면 설명` → Tooltip; `눌러서 펼치는 메뉴` → Dropdown/Popover; `검색해서 고르기` → Combobox.
- 모호한 `팝업`, `말풍선`은 관련 후보 여러 개와 차이를 보여 준다. 무조건 하나로 단정하지 않는다.
- 검색어가 없어도 카테고리별 시각 카드로 둘러볼 수 있다. 정식 명칭만 나열한 목록으로 대체하지 않는다.
- 결과 없음 상태에는 검색어 초기화와 가까운 카테고리를 제공한다. 검색·필터·스크롤 위치는 상세에서 돌아와도 유지한다.

### 7.2 이해하기

모든 항목은 쉬운 설명, 정식 이름, 쓰는 상황, 피할 상황, 비슷한 요소와의 차이, 레시피 견본을 갖는다. 예를 들어 Toast는 일시적인 처리 피드백, Alert Dialog는 사용자 결정을 기다리는 중요한 확인, Banner는 지속적으로 보이는 안내라는 차이를 설명한다.

라이브러리 패키지 이름은 정식 컴포넌트 개념과 분리한다. Drawer/Sheet, Toast/Snackbar와 같은 별칭은 검색에 포함하지만 실제 구현 라이브러리에서 동작이 완전히 같다고 보장하지 않는다.

### 7.3 후보 비교

- 모든 종류에 최소 3개의 구별되는 시각 레시피를 제공한다. 총 최소 108개다.
- 레시피 차이는 면·선·모서리·여백·배치·아이콘·액션 구조 중 실제로 식별할 수 있는 차이를 포함한다. 색·라이트/다크·성공/실패 상태만 바꾼 것은 새 레시피로 세지 않는다.
- Toast 예: 중립 면+상태 아이콘, 상태색 면, 실행취소 액션 강조형. Dialog 예: 중앙 정렬 확인형, 왼쪽 정렬 작업형, 폼 중심형. Alert 예: 은은한 면, 테두리형, 제목·액션 배치형.
- 후보는 같은 크기의 비교 영역, 문구·데이터·상태에서 나란히 본다. 차이와 추천 용도를 짧게 표시한다.
- 현재 팔레트·폰트·형태와 라이트/다크가 적용된다. 최대 3개의 후보를 비교함에 담을 수 있다.
- 카드를 열거나 후보를 체험하는 것은 현재 디자인을 바꾸지 않는다. `내 디자인에 적용`에서만 선택이 바뀐다.

### 7.4 실제 동작과 상태

정적인 견본은 팜플렛처럼 열람할 수 있고, 별도 `실행`에서 실제 동작을 체험한다. 버튼을 눌러 토스트 띄우기, 다이얼로그 열고 닫기, 메뉴 탐색, 폼 입력·검증, 표 정렬·샘플 필터링과 페이지 변경 등이 대상이다.

컴포넌트별 상태 지원표를 둔다. 가능한 경우 default, hover, pressed, focus-visible, disabled, loading, error, empty, selected를 제공한다. 의미 없는 상태를 억지로 만들지 않는다. 긴 한국어·영어 문구와 좁은 화면도 체험할 수 있게 한다.

모달의 초점 진입·가두기·복귀, 취소와 닫기, 메뉴/콤보박스의 키보드 이동, Tooltip의 키보드 노출, Toast의 상태 알림, 탭 의미 구조를 실제로 확인한다. 영구 견본마다 live announcement를 반복하지 않고 실행한 피드백에서만 적절히 알린다. reduced-motion도 반영한다.

File Upload는 브라우저 로컬 파일 선택·이름 표시와 샘플 검증만 수행한다. 업로드 API나 외부 전송을 만들지 않는다. 데모 선택 파일·입력 내용은 디자인 프로필에 저장하지 않는다.

### 7.5 현재 디자인에 연결

- 프리셋의 기본 레시피와 사용자가 바꾼 레시피를 구별한다.
- 요소별 `프리셋 기본값으로 복원`과 최근 적용의 실행취소를 제공한다.
- 색상은 표면·포인트·상태 등 허용된 의미 역할에서 고른다. 상태 의미를 임의의 포인트색으로 치환하지 않는다.
- 지원하는 요소에 한해 크기·밀도·모서리·테두리·그림자·표시 위치·정렬 등을 미리 정의된 선택지로 다듬는다. 자유 픽셀 편집기는 만들지 않는다.
- 적용 시 현재 화면에 그 요소가 없다면 상태를 명확하게 알리고 도감 내 해당 요소 미리보기로 확인하게 한다. 모든 요소를 화면 안에 억지로 배치하지 않는다.

## 8. 선택 상태, 변경과 저장

선택 상태는 한 개다. 현재의 palette/style/fonts/icons/target/scope/framework/layout에 아래 구조를 확장한다.

- `screenPreset`: 선택한 완성 프리셋 ID, 선택하지 않았으면 null.
- `previewScreen`: 현재 확인하는 샘플 화면. 기존 앱의 layout 결정과 별개다.
- `componentOverrides`: 종류별 레시피 ID 및 해당 레시피가 허용한 옵션의 변경분.
- 카탈로그 버전: 프리셋·레시피 ID의 의미를 재현하는 버전.

**디자인 참고 범위와 실제 수정 범위는 분리한다.** 상태·프로필에 `changeIntent`와 `componentTargets`를 함께 기록한다.

| changeIntent | 진입과 의미 | 실제 적용 범위 |
|---|---|---|
| whole-design | 완성 프리셋을 명시적으로 적용 | 전역 선택과 전체 레시피를 기준으로, 대상 앱에 이미 있거나 요청한 기능에 필요한 요소를 적용 |
| component-only | 프리셋 선택 없이 도감에서 요소를 적용 | componentTargets에 기록한 요소만 수정. 다른 요소·전역 팔레트·폰트·레이아웃을 변경하지 않음 |
| legacy-theme | 기존 색상·스타일·폰트 선택에서 이관 | 기존 동작과 scope를 유지하고 선택하지 않은 컴포넌트의 새 교체 지시를 만들지 않음 |

component-only에서는 `componentTargets`가 비어 있으면 적용용 내보내기를 막고 요소 선택을 안내한다. Toast를 적용했다면 Toast만 들어간다. 이때 전역 팔레트와 폰트는 도감의 비교 조건이며 앱 전체 변경의 권한이 아니다. 에이전트는 선택한 요소 안에서 기존 의미 토큰을 우선 매핑하고, 필요한 별도 값이 있으면 그 요소로 한정한다. 모드 scope와 지정하지 않은 동작은 유지한다.

whole-design에서는 프리셋의 36종을 전체 참고 기준으로 기록하지만, 없는 요소 36종을 새 기능으로 추가하라는 지시로 만들지 않는다. 프리셋을 적용한 뒤 도감에서 일부 요소를 바꿔도 whole-design 의도는 유지된다. component-only에서 처음 완성 프리셋을 적용하면 전체 디자인 범위로 넓어진다는 점을 적용 요약에 표시한다. legacy-theme에서 처음 도감 요소를 적용하면 기존 전역 선택의 적용 의도를 유지하며, 명시한 요소만 새 컴포넌트 수정 대상으로 추가한다. 이 경우 changeIntent는 legacy-theme를 유지하고 componentTargets를 함께 기록한다.

해석 순서는 프리셋 기본 선택 → 사용자가 변경한 전역 값 → 컴포넌트 레시피와 옵션 변경분이다. 새 전역 팔레트를 적용하면 모든 요소가 그 팔레트의 의미 토큰으로 다시 그려지며, 개별 레시피 선택은 유지한다. 프리셋을 바꾸면 적용 예정인 전역 값·기본 레시피와 제거될 변경분을 요약하고, **전체 적용 / 내 세부 수정 유지 / 취소**를 선택하게 한다. 어느 경로든 조용히 변경분을 삭제하지 않는다.

레시피 교체 시 이전 레시피에서만 유효한 옵션을 숨겨 보존하지 않는다. 호환되는 공통 옵션만 유지하고 제거되는 옵션을 요약한다. 실제 해석 결과와 프롬프트에는 현재 유효한 값만 들어간다.

로컬 저장과 URL fragment로 선택을 재현한다. 즐겨찾기와 비교함은 개인 탐색 상태이며 에이전트 프로필에 섞지 않는다. fragment에는 버전·ID·허용된 선택값만 넣고 파일·이미지를 넣지 않는다. 인코딩 결과가 8 KiB를 넘으면 파일 내보내기로 안내한다. 다른 기기의 자동 동기화를 약속하지 않는다.

유효하지 않은 ID/옵션, 손상된 저장값과 지원하지 않는 미래 버전은 명시적으로 처리한다. 모르는 항목을 조용히 다른 디자인으로 바꾸고 동일하게 복원됐다고 표시하지 않는다.

## 9. 데이터와 렌더링 구조

프리셋, 컴포넌트 정의, 레시피, 화면 템플릿을 분리한다. 아래는 제안 경로이며 구현자가 동일한 책임을 유지하는 모듈 구조로 조정할 수 있다.

- `data/screen-presets.*`: 전역 초기 선택, 종류별 기본 레시피, 설명·태그.
- `data/component-catalog.*`: 안정적 ID, 한국어/영문/별명, 용도·차이, 지원 상태·옵션.
- `data/component-recipes.*`: 안정적 레시피 ID, 스타일 참조, 의미 토큰 매핑, 구체적 치수·동작 기본값.
- 공통 선택 해석기: 설정을 검증하고 최종 컴포넌트 명세를 계산하는 순수 함수.
- 공통 컴포넌트 렌더러: 도감 견본·실행 영역·화면 미리보기에서 재사용.
- 공통 핸드오프 생성기: 같은 최종 명세를 읽어 JSON·CSS·문서·프롬프트를 생성.

핵심은 UI DOM에서 문구를 추출해 프롬프트를 만드는 방식이 아니라, 검증된 선택을 해석해 모든 출력을 만드는 것이다. 선택한 화면만 렌더링하고 보이지 않는 체험 인스턴스는 정리한다. 모든 팔레트×모드×레시피를 동시에 DOM에 만들지 않는다. 타이머·리스너·중복 ID·중첩 모달이 화면 전환 뒤 남지 않게 한다.

## 10. 에이전트 핸드오프와 호환성

새 기능을 선택한 프로필에는 선택 의도와 **최종 해석된 컴포넌트 명세**를 함께 기록한다. whole-design은 전체 레시피를, component-only는 componentTargets의 명세만, legacy-theme는 명시적으로 추가한 대상이 있을 때 그 명세만 내보낸다. 각 출력에는 changeIntent와 실제 적용 범위를 명시한다. 카탈로그 ID만 전달해 에이전트가 원본을 찾아야 구현할 수 있는 상태로 만들지 않는다. 화면에서 표시한 값과 내보낸 값은 일치해야 한다.

출력:

| 파일 | 역할 |
|---|---|
| handoff-config.json | 편집 가능한 사용자 선택과 카탈로그 버전 |
| design-profile.json | 최종 팔레트·폰트·레이아웃·요소별 레시피·치수·동작·의미 토큰 |
| design.md | 전체 디자인 의도와 선택한 컴포넌트별 구현 기준 |
| AGENT-TASK.md | 한국어 작업지시, 적용 범위와 구체적인 선택 요약 |
| selected-theme.css / selected-style.css / selected-fonts.css | 현재와 같은 역할별 CSS |
| selected-components.css | 선택 레시피의 시각 기준을 확인하는 scoped 참고 CSS |
| QA-CHECKLIST.md | 선택한 동작·상태·반응형을 실제로 확인할 항목 |

프롬프트는 예를 들어 토스트의 레시피, 표면·글자·상태 아이콘 역할, 위치, 폭·모서리, 유지 시간, 닫기·실행취소 여부를 명시한다. 다이얼로그에는 크기·버튼 배치·취소/닫기·키보드와 초점 복귀를 명시한다. 단순히 '모던하게 구현'으로 대체하지 않는다.

수치와 동작은 선택한 레시피의 실제 데이터에서 생성한다. 허용 scope, changeIntent, componentTargets, 기존 업무 기능 유지, 기존 컴포넌트/ThemeProvider 재사용을 전달한다. 모든 프리셋에서 새 컴포넌트를 일괄 생성하지 말라는 규칙도 넣는다. shadcn/Radix/Sonner를 이미 쓰는 앱에서는 해당 구현에 매핑할 수 있지만, 이 키트의 프리뷰 CSS와 클래스를 앱의 필수 런타임으로 강요하지 않는다. 기존 테마 변경 범위와 전역 폰트 범위의 차이도 그대로 유지한다.

브라우저·CLI는 `data/handoff-core.js`를 중심으로 동일한 생성 규칙을 사용한다. 신규 프로필은 major version을 올려 3.0.0으로 식별하고, 설정 스키마도 버전을 표시한다. 기존 v2 설정과 프로필을 읽는 경로는 유지한다. 도감 필드가 없는 기존 선택에는 `screenPreset=null`, 빈 componentOverrides를 적용하고, 이전 외형을 임의의 새 프리셋으로 교체하지 않는다. 레거시 선택에서는 선택하지 않은 컴포넌트의 교체를 새 작업지시로 추가하지 않는다. 기존 v1 브라우저 저장값/URL 이관도 회귀 확인한다.

브라우저 내보내기는 현재와 같이 텍스트 산출물을 저장할 수 있다. CLI는 선택한 폰트·아이콘과 라이선스를 함께 복사한다. 브라우저가 ZIP·WOFF2 묶음을 제공한다고 허위로 안내하지 않는다. `--check`는 여전히 무변경 검사다.

## 11. 화면 품질, 반응형과 배포

데스크톱에서는 탐색/상세 조정 중에도 결과 미리보기를 유지한다. 모바일은 탐색·큰 미리보기·내 디자인으로 이동할 수 있고, 하단 고정 UI가 본문이나 포커스를 가리지 않게 한다. 도감에서 터치로도 모든 핵심 설명과 실행에 접근할 수 있어야 한다.

기존 `index.html`을 기본 진입점으로 확장하고, `icons.html`과 `handoff.html`은 공유 선택 상태와 연결한다. 오프라인 폴더 배포와 단일 `START-HERE.html`의 새 기능 포함 여부를 명확하게 일치시킨다. 이번 변경에서 단독 실행에 필요한 스크립트·CSS를 번들러에 의도적으로 반영하고 실제로 새 도감을 포함한 번들을 검증한다. 변경 없는 아이콘 작업처럼 무관한 이유로 재번들하는 것은 아니다.

폰트 카탈로그·바이너리는 중복 동봉하지 않고 기존 로더를 재사용한다. README의 기능 설명·동선·실제 스크린샷과 스크린샷 신선도 검사는 변경된 화면에 맞춰 갱신한다. 신규 외부 서비스·호스팅이나 npm 공개 배포는 이번 설계에 포함하지 않는다.

## 12. 구현 완료를 판단할 검증

1. 도감에 36종과 최소 108개 구별되는 레시피가 존재하고 모든 항목에서 설명·비교·체험·선택이 가능하다. 항목 수만 맞추고 실제 동작·전달이 빠진 경우 미완료다.
2. 위 필수 한국어 설명 검색과 모호한 검색의 다중 후보가 작동한다. 도감 단독 진입도 가능하다.
3. 6개 프리셋을 4종 화면에서 확인할 수 있고 같은 데이터·문구를 사용한다. 모바일·라이트·다크에서도 선택 결과를 확인한다.
4. 화면에서 요소 선택 → 도감에서 레시피 적용 → 화면 복귀가 연결된다. 없는 요소는 도감 미리보기에서 확인한다.
5. 팔레트 변경 시 레시피가 유지되고, 프리셋 변경 시 변경분 유지/초기화/취소가 선언한 대로 동작한다. 실행취소와 기본값 복원도 확인한다.
6. 브라우저·CLI 출력이 같은 선택에 대해 동일하다. 저장/복원 후에도 화면과 최종 컴포넌트 명세가 일치한다. 프리셋 없이 Toast만 적용하면 Toast만 수정 대상으로 출력되고, 프리셋 적용은 전체 디자인 기준이 되며 불필요한 새 기능을 추가하지 않는다. 알 수 없는 ID와 옵션, 미래 버전은 명확한 오류 또는 복구 안내가 있다.
7. 기존 프로필·URL·scope·폰트·아이콘·CLI --check 동작을 유지한다. 새 도감 선택이 없는 레거시 선택의 지시 범위를 넓히지 않는다.
8. 키보드와 초점 이동, 모달 복귀, 메뉴·콤보박스, Tooltip, Toast 알림, reduced-motion, 긴 문구와 작은 화면을 실제 브라우저에서 확인한다.
9. 의미 토큰 대비 검사를 확장하고, 정적 통과를 제품 전체 접근성 인증으로 표현하지 않는다.
10. 오프라인 폴더 실행과 단독 실행 번들에서 핵심 여정이 작동한다. UI 스크린샷과 README가 실제 화면에 맞는다.

검증은 카탈로그 무결성·선택 해석·이관·브라우저/CLI 동일성처럼 실질적인 계약을 자동화하고, 실제 인터랙션은 브라우저로 확인한다. 기존 `scripts/check-studio-flow.cjs`, `scripts/check-handoff-browser.cjs`, `scripts/test-design-handoff.cjs`, `scripts/check-handoff-schemas.cjs`, `scripts/check-integration.cjs`, `scripts/audit.mjs`의 관련 검사를 재사용·확장한다. 단순 표시 문구를 그대로 복제하는 테스트는 추가하지 않는다.

## 13. 구현자가 결정할 세부 사항

- 모듈 파일명, 코드 분할 방식, 렌더링 최적화의 구체적 구현.
- 기존 카탈로그 범위 안에서 프리셋별 폰트·아이콘과 각 레시피의 구체적인 수치. 선택 이유와 미리보기 결과를 남긴다.
- 원칙을 만족하는 구체적인 데스크톱·모바일 배치와 문구.
- 한국어 검색 별명 추가, 종류별 지원 상태표, 공통 옵션 범위.

이 결정들 때문에 같은 제품 방향을 다시 질문할 필요는 없다. 사용자가 고른 흐름·독립 도감·충분한 미리보기·선택의 재현과 핸드오프라는 핵심 계약을 유지한다.
